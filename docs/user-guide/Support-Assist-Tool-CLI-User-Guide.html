CLI User Guide

Support Assist Tool v0.5.0: CLI User Guide

The command line for Veeam support casework: gathering evidence from a customer machine, parsing a bundle, checking a file, and proving a connection.

Introduction

About this guide

This guide covers the command line of Support Assist Tool 0.5.0. The same verbs exist on Windows and Linux, except those listed under Windows-only verbs.

The CLI is the same executable as the graphical application. Run with no arguments, it opens the GUI; run with a command, it runs the command. Run with only file or folder paths, which is what the desktop passes when files are dropped on the executable, it opens the GUI with them: each file's SHA-256 is shown and a folder is offered to Log Review.

Use the CLI when there is no desktop to run a GUI on, when the work is done over SSH, or when the same collection has to be repeated the same way on several machines.

The changes of 0.5.0 are listed in What’s New.

Introduction > What’s New in v0.5.0

What’s New in v0.5.0

Support Assist Tool 0.5.0 is the first release of the 0.5 line, the Beta. This article lists the changes to the command line. The other changes are in the Windows User Guide and the Linux User Guide.

Command Line

  • SQL Tools. sql check, shape, backups, files and query, with --engine postgres and --show-sql; sql instances and sql databases.
    • sql query prints its statement first, then a table or a block per row. --format table|records|tsv chooses the layout.
    • --query takes a named query's name, such as Backup audit (this database) for SQL Server or Backup readiness (WAL archiving and slots) for PostgreSQL.
  • Guided Diagnostics. guided scenarios and guided run. --input vbr_version=12 tests the ports of VBR 12; left out, the managed server scenario tests both versions.
  • Ports. network presets lists the ports of VBR 12 and VBR 13 for each role and marks a port only one version lists as VBR 12 only or VBR 13 only.
  • Host checks. system host-checks, system pipes (named pipes on Windows, Unix sockets on Linux), system installer-cache on Windows, and network service-channel.
  • WMI. wmi health, and wmi query --user, which reads the password from SAT_WMI_PASSWORD.
  • Packets. packet events lists the notable events in a .pcapng or .pcap.
  • Change analysis. files compare and registry compare take --keep, which keeps the compare in the capture file. baseline inspect lists a capture, how it was read and the compares kept in it.
  • Collections. logs gather and logs universal include the kept tool output in the collection.
  • Integrations. tools run runs the guided runs of Integrations: iPerf3, tcpdump on Linux and ETL2PCAPNG on Windows.
  • Diagnostics. diagnostics prints what the tools need on this machine.

Security and Downloads

  • Libraries. The packages on Windows and Linux carry OpenSSL 3.5.9 and libarchive 3.8.10.

Requirements

SAT runs with no installation and leaves nothing behind. It is copied onto a machine, run, and removed. Nothing is installed, no service is registered, and no runtime has to be present first.

Supported operating systems

PackageBuilt onRuns on
Windows (SupportAssistTool.exe)Windows x64, statically linkedWindows 10, Windows 11 and Windows Server 2016 or newer, x64
Linux CLI (-linux-x64-cli)glibc 2.28 (AlmaLinux 8 / RHEL 8 family)Any x86-64 Linux with glibc 2.28 or newer: RHEL, CentOS, Alma and Rocky 8 or newer, Debian 10+, Ubuntu 18.04+, SLES 15+
Linux GUI (-linux-x64)glibc 2.34 (AlmaLinux 9 / RHEL 9 family)Any x86-64 Linux with glibc 2.34 or newer, with X11 or Wayland

A binary runs on the glibc it was built against and on newer ones. That is why the CLI is built on the older base: it covers the wider range of customer machines. The graphical package needs a newer distribution than the command-line one.

Third-party software you must install

None. There is nothing to install to run SAT, on either platform.

  • Windows links its dependencies statically. No Visual C++ redistributable and no .NET runtime is required.
  • Linux carries its own libraries in ./lib beside the executable, resolved through an $ORIGIN/lib runpath. The CLI package bundles libarchive, OpenSSL (libssl and libcrypto), SQLite, zlib, zstd, lzma and bzip2. The GUI package adds libssh2 for Remote (SSH), unixODBC for SQL Tools, libxml2, Qt 6, X11/XCB, Wayland, fontconfig, FreeType, HarfBuzz and ICU. lib/RUNTIME-LIBRARIES.txt lists what a package carries, and lib/Verify-Runtime.sh shows how each one resolves. Only glibc and the ELF loader come from the host.

Because the libraries travel with the package, copy the whole folder. The executable does not start without the lib directory beside it.

Privileges

SAT runs as an ordinary user. Some readings need elevation: Windows servicing-package inventory needs an administrator, and some Linux host details need root. When a reading is skipped for that reason, the command names it and continues. Run as an ordinary user unless a reading says it needs elevation.

Introduction

Run the CLI

Unpack and run. There is no installer and no uninstall.

Before You Begin

  • Linux: an x86-64 machine with glibc 2.28 or newer for the command-line package. See Requirements.
  • Windows: nothing. SupportAssistTool.exe is the whole program.
To run the CLI on Linux, do the following:
  1. Extract the package: tar xzf Support-Assist-Tool-0.5.0.6-linux-x64-cli.tar.gz.
  2. Change into the folder: cd Support-Assist-Tool-0.5.0.6-linux-x64-cli.
  3. Run ./SupportAssistTool version.
Expected result. The command prints the full version and the date the build was made.
To run the CLI on Windows, do the following:
  1. Open a command prompt or PowerShell in the folder that holds SupportAssistTool.exe.
  2. Run a command, for example SupportAssistTool.exe capabilities > capabilities.json.
Expected result. Output can be redirected and piped normally.

To remove SAT, delete the folder. Case data, reports and collections are written only where you point them.

Introduction

Command shape and exit codes

Commands are SupportAssistTool <area> <verb> [options]. --help lists every verb available on the current platform.

Exit codes are meant to be tested in a script:

CodeMeaning
0Success, or completed with no findings
2Not available on this host, or not applicable
3Completed and found something (comparison and diagnostic commands only)
64The command line was wrong
70The operation failed
74tools review only: the source could not be read
130Cancelled

Exit 3 is not an error. It means the command completed and found something, such as findings in a log review or a file that does not match its expected SHA-256. Test for it explicitly in a script.

help and --help print the commands and their options, and version or --version prints the full version. A command or option that is not known is named on the error stream with the words Unknown command or Unknown option, and the nearest option is suggested; the exit code is 64.

Paths are read as typed, in any language. On Windows a file or folder named with characters outside the system code page, such as Japanese or Polish letters, works in every command.

To test a command's result in a script, do the following:
  1. Run the command.
  2. Read $? in a shell, or %ERRORLEVEL% in a command prompt.
  3. Treat 0 and 3 as a completed run, and 2, 64, 70, 74 and 130 as listed in the table.
Expected result. Exit 3 is a completed run that found something. See Using SAT from a script.

Create a case

case create makes a case workspace: a folder named for the case ID under the parent folder, holding the logs, captures, reports, parsed data, parser cache and baselines folders the rest of SAT writes into.

Before You Begin

  • Choose a parent folder that the account can write to.
  • Have the case ID. The folder takes its name.
To create a case, do the following:
  1. Run case create with the parent folder and the case ID.
  2. Read the paths the command prints: the workspace and its Logs, Captures, Reports, Parsed, Parser cache and Baselines folders.
Expected result. The case workspace exists and the other commands can write into it with --case or --output.
SupportAssistTool case create --parent D:\cases --id 05412345 \
    --title "VAW backup failure" --engineer "A. Engineer"
OptionWhat it does
--parent DIRThe folder the case folder is created in. Required.
--id CASE-IDThe case identifier, used as the folder name. Required.
--title TEXTA readable title, stored in the case record.
--engineer NAMEThe engineer's name, stored in the case record.
--notes TEXTA note stored in the case record, case.json.

The graphical application opens the same workspace from Case Manager.

Gather support logs

logs gather detects the Veeam products present and collects their support logs, plus enough platform context to interpret them. logs universal is the same command.

Before You Begin

  • Run on the machine whose logs are wanted. An ordinary user collects what that account can read; some logs need administrator or root.
  • Run the tools whose output belongs in the collection first. The collection takes the tool output kept beside SAT in Log-Collections/Tools, archives it with the logs and removes it after a finished archive.
  • Choose an output folder, such as the case's logs folder.
To gather the support logs of a machine, do the following:
  1. Run logs gather --output DIR.
  2. Read the summary: the platform, the detected products and roles, the collection folder, the files collected, the exporter runs and the third-party error logs.
  3. Read the clock line and the archive path, then transfer the archive.
Expected result. The command exits 0 when the collection finished. A warning is printed on its own line.
SupportAssistTool logs gather --output D:\cases\05412345\logs
OptionWhat it does
--output DIRWhere the collection is written. Required.
--no-archiveLeaves the collection as a folder and makes no archive.
--days NCollects the logs of the last N days, from 1 to 3650.
--official-exportersAlso runs the vendor's own log exporters. They take considerably longer and can load a production machine, so they run only when this option is given.
--no-third-party-errors, --no-platform-contextNarrow what is collected.

If no Veeam product is found, the command still collects system and support context and says so. That is the normal result on a repository or an NFS/SMB target, which holds backups without running Veeam software locally.

Targeted collection

logs collect is the narrower form, for when you know which product's logs you want and over which period.

Before You Begin

To collect one product's logs for a period, do the following:

Review a bundle

logs review parses a bundle and writes the report an engineer reads. It accepts a folder, an archive, or several of either.

SupportAssistTool logs review --path ./Support-Assist-Tool-vaw-2026-08-10.zip \
    --output review.txt
SupportAssistTool logs review --path ./vbr-bundle --path ./agent-bundle \
    --profile auto --case D:\cases\05412345 --json

By default it builds a fast index first: the high-value identity, service, job and rescan logs are parsed immediately and the data-mover logs are catalogued but deferred. --full-scan includes everything.

OptionEffect
--profileauto (the default) detects each source's product; vaw, vbr, sql-plugin, rman-plugin or generic forces one parser.
--case CASE_ROOTSaves the review into that case workspace.
--from, --to, --date-orderBound the review to a period. --date-order (mdy, dmy, iso, system or auto) says how to read a date that could be day-first or month-first.
--assumed-offset-minutes NThe UTC offset applied to log timestamps that carry none.
--find TEXT, --case-sensitiveAdds the lines that contain the text to the review as informational findings.
--context N, --max-incidents NLines of context kept before and after each finding (5 by default), and a ceiling on grouped findings.
--cache-dir DIR, --no-cacheWhere parsed results are cached between runs, or no cache.
--multi-machine-sourceTreats one source as holding several machines. Without it, each source is one primary machine.
--discover-veeamReviews the Veeam log folders found on this machine.
--no-archives, --no-warningsSkips archives inside the sources, or leaves warnings out of the report.
To review a bundle, do the following:
  1. Run logs review with one --path for each folder, archive or file.
  2. Add --case CASE_ROOT to save the review into a case, or --output to name the report.
  3. Read the summary, then the report.
Expected result. The report holds the machine, the product, the runs and the grouped findings. The exit code is 3 when findings were present.

The report is the same on every platform. The same bundle parsed on Windows and on Linux produces byte-identical output, so a report made on one can be compared with, or continued on, the other.

Exit code 3 means findings were present, which is the usual outcome for a case.

Worker threads, CPU and how long a review takes

Log Review parses files in parallel. By default SAT uses one worker per logical processor, capped at eight and never more than the number of files it found. The cap leaves room for the other work a customer machine is doing.

Consider the host before raising it. On a backup server inside its backup window, on a proxy that is moving data, or on a repository under load, extra parser threads compete with the customer's own jobs. On a machine with slow storage the review is bound by disk, and more workers do not help.

Every review reports what it used: Workers Used, Elapsed and Throughput in lines per second are printed with the summary and written into the report. Run once, read those three numbers, and adjust only if they justify it.

SettingEffect
DefaultOne worker per logical processor, capped at eight and at the file count.
--workers NFixes the worker count. Clamped to at least one and never above the file count.
--single-threadOne worker. Use on a production host under load, or when isolating a parser problem.

Search logs

logs search looks through logs in place, without building a review index. Use it when you already know what you are looking for.

Before You Begin

  • Have the folder, the archive or the file to search, or use --discover-veeam for this machine's Veeam log folders.
  • Have the text or the regular expression.
To search logs for a text, do the following:
  1. Run logs search with --path and --text.
  2. Add --max-results and --format csv --output hits.csv to keep the hits in a file.
  3. Read each hit: the severity, the source path, the line number and the matching text.
Expected result. Each hit carries its source path and line number.
SupportAssistTool logs search --path ./logs --text "not enough space" \
    --max-results 50 --format csv --output hits.csv
SupportAssistTool logs search --discover-veeam --regex "Error.*timeout" --pattern "*.log"
OptionWhat it does
--path DIRA folder, archive or file to search. Repeat it for several.
--discover-veeamSearches the Veeam log folders found on this machine.
--text TEXT, --regex REGEXLiteral text, or a regular expression.
--pattern GLOBLimits the search to matching file names.
--severity VALUEFilters by level.
--case-sensitiveMatches letter case.
--context NLines of context kept with each hit, 4 by default.
--max-results NStops after N hits.
--from, --to, --date-order, --assumed-offset-minutesBound the period and say how to read dates, as for logs review.
--no-archivesSkips archives inside the sources.
--output FILE, --format text|html|json|csvWhere the hits are written, and in which form.

Rebuild from a collection

logs reconstruct rebuilds environment.log and <MACHINE>-SystemHealth.txt from a collection that carries only raw evidence, so Environment Review and Health Monitor can open it.

SupportAssistTool logs reconstruct --path ./Support-Assist-Tool-vbr-2026-09-01 \

The command lists anything it could not rebuild, and why. health load accepts the same collection folder directly; see Health snapshot.

To rebuild the reports of a collection, do the following:
  1. Run logs reconstruct --path COLLECTION_DIR --output DIR.
  2. Read the list of anything that could not be rebuilt, and why.
  3. Open the output folder in Environment Review and Health Monitor, or run health load on it.
Expected result. environment.log and <MACHINE>-SystemHealth.txt are in the output folder.

Review tool output

tools review reads the output of the tools run on Customer / Lab machines and lists it by machine, in UTC order.

SupportAssistTool tools review --source ./bundle/Tools
SupportAssistTool tools review --source D:\Log-Collections --machine SQL01 --note

--source takes a bundle's Tools folder, a Log-Collections tree, or any folder above them. --machine keeps one machine's runs, --json prints the timeline as JSON, and --note formats it for pasting into a case note. Exit 74 means the source could not be read.

To review tool output as a timeline, do the following:
  1. Run tools review --source DIR on the bundle's Tools folder or on the folder above it.
  2. Add --machine NAME to keep one machine's runs.
  3. Add --note to format the timeline for a case note, or --json for a script.
Expected result. The runs are listed by machine in UTC order. Exit 74 means the source could not be read.

Host checks

Health snapshot

health sample takes a point-in-time snapshot of CPU, memory, paging, volumes and network adapters, and raises findings against thresholds.

SupportAssistTool health sample --output system-health.txt
SupportAssistTool health load --input system-health.txt
SupportAssistTool health load --input ./Support-Assist-Tool-vbr-2026-09-01 --output summary.txt

health load opens a snapshot captured anywhere, including one saved by the graphical application on another platform. Given a collection folder, it reads the collection's own saved snapshot, or a snapshot rebuilt from the raw evidence when the collection has none.

To take and read a health snapshot, do the following:
  1. Run health sample --output system-health.txt on the machine.
  2. Run health load --input system-health.txt on any machine to read it. Give a collection folder to read the collection's own snapshot.
Expected result. The snapshot lists CPU, memory, paging, volumes and network adapters, with findings against thresholds.
Host checks

Diagnostics

diagnostics reports how SAT itself is running: elevation, session, working directory and the privileges it holds.

SupportAssistTool diagnostics
SupportAssistTool diagnostics --include-user --json

diagnostics also lists what the tools need on this machine: glibc, the kernel, unixODBC, the ODBC drivers for SQL Server, psql and whether SAT runs as root on Linux; the Windows build, .NET, PowerShell, the services SAT reads, administrator rights, the ODBC drivers and psql on Windows. --include-user adds the account context. Capture this first when a command reports something as unavailable, because elevation is usually the reason.

To read the runtime context, do the following:
  1. Run diagnostics, or diagnostics --include-user --json for a script.
  2. Read the elevation, the session, the working directory and the requirements.
Expected result. Run this first when another command reports a reading as unavailable.
Host checks

File checksums

files hash prints the SHA-256 of each file it is given, reading the file in place. Use it to confirm that a download, a patch or a log bundle is the file it should be.

SupportAssistTool files hash --path ./VeeamBackup&Replication_12.3.iso
SupportAssistTool files hash --path ./setup.exe \
    --expect 9f2c4b1a7e3d5f60a8b9c0d1e2f3a4b5c6d7e8f90a1b2c3d4e5f60718293a4b5
SupportAssistTool files hash --path ./bundle-a.zip --path ./bundle-b.zip --json

Each file is printed in the layout certutil -hashfile uses on Windows: the file name between two rules, then its SHA-256, its size and its full path.

========================================
setup.exe
========================================
SHA256  9f2c4b1a7e3d5f60a8b9c0d1e2f3a4b5c6d7e8f90a1b2c3d4e5f60718293a4b5
Size    1.21 GiB (1300234752 bytes)
Path    D:\downloads\setup.exe
Match   yes, expected 9f2c4b1a7e3d5f60a8b9c0d1e2f3a4b5c6d7e8f90a1b2c3d4e5f60718293a4b5

--expect takes a published SHA-256 value and compares every file with it. Letter case and spaces are ignored, so a value copied from a download page, or from older certutil output with a space between each pair of bytes, can be pasted as it is. --json prints one record per file, with matches_expected when --expect is given.

Checking a SHA256SUMS list

--check reads a checksum list and checks every file it names, looking for each one beside the list, as sha256sum -c does. A list is read in the form sha256sum writes, <value> <name> or <value> *<name>, or in the form SHA256 (<name>) = <value>. A file named <name>.sha256 or <name>.sha256sum that holds a single value checks <name>. --check can be given more than once, and together with --path.

SupportAssistTool files hash --check ./SHA256SUMS
SupportAssistTool files hash --check ./tool.zip.sha256 --json
========================================
SHA256SUMS
========================================
OK       good.zip
FAILED   changed.zip
         expected ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad
         found    a52d159f262b2c6ddb724a61840befc36eb30c88877a4030b65cbe86298449c9
MISSING  not-downloaded.zip
NOT READ ../outside.zip
         The name points outside the list's folder.
4 listed: 1 OK, 1 FAILED, 1 MISSING, 1 NOT READ

Only files in the list's folder, or below it, are read. A name that is absolute, starts with a drive or a server, or climbs out with .. is reported as NOT READ and is not opened. With --json, each list is a record under checks, with an entry per file giving its status, the expected value and the sha256 found.

Exit codeMeaning
0Every file was read, and matched --expect when it was given
3At least one file does not match --expect, or a file a list names does not match it or is missing
64The --expect value is not a SHA-256 value
70A path is a folder, is missing, is not a regular file, or could not be read; a list could not be read or is not a checksum list; or a file a list names could not be read or points outside the list's folder

Only regular files are read. A folder, a device or a pipe is reported against its path, and the remaining files are still hashed.

To verify a file against a published SHA-256, do the following:
  1. Run files hash --path FILE --expect VALUE, with the value copied from the download page.
  2. Read the Match line and the exit code.
Expected result. Exit 0 means the file matches. Exit 3 means it does not.
To check a SHA256SUMS list, do the following:
  1. Download the list next to the files it names.
  2. Run files hash --check ./SHA256SUMS.
  3. Read the line for each file: OK, FAILED, MISSING or NOT READ.
Expected result. The last line counts the files listed and how many are OK, FAILED, MISSING and NOT READ.
Tools

Network tools

Proving whether a connection works, from the machine that has the problem: a port, a TLS handshake, a path toward this machine, and throughput between two machines.

Before You Begin

  • Run the test on the machine that fails, toward the machine it fails to reach. Direction matters.
  • Get the target and the port from the failing log line. Ports differ by role; network presets lists them.
  • To test the SAT payload or a UDP result, start a listener on the other machine first. A port below 1024 needs root for the listener.
  • Allow the port in every firewall between the two machines.
To test whether a TCP port is reachable, do the following:
  1. Run network test --host HOST --port PORT.
  2. To prove the path from every local interface, add --all-interfaces. A Veeam host often has a management NIC and a separate backup NIC, and a ping that works does not show which one a job uses.
  3. Read the result: the source address used, the time taken and whether the connection succeeded.
Expected result. Against a SAT listener, the two ends exchange a handshake and a 50 MB test payload, and the payload's SHA-256 is checked on arrival.
SupportAssistTool network interfaces
SupportAssistTool network test --host repo01 --port 6160
SupportAssistTool network test --host repo01 --port 6160 --all-interfaces
OptionWhat it does
--host HOST, --port PORTThe target. Required.
--timeout-ms NHow long to wait for the connection, 5000 by default.
--source IP, --interface NAMEThe local address or interface the test starts from.
--all-interfaces, --include-virtualTries each local interface in turn; the second adds virtual adapters to that set.
--sat-payload SIZEThe payload sent to a SAT listener, 50M by default.
--no-sat-payload, --no-sat-handshakeKeep the handshake and skip the payload, or make a plain connect test.
To check a TLS handshake, do the following:
  1. Run network tls --host HOST --port PORT.
  2. Add --compare-versions to try TLS 1.2 and 1.3 separately, or --version 1.2 or --version 1.3 to force one.
  3. Add --expected-fingerprint HEX to check the certificate against a known value, and --sni NAME when the server name differs from the host.
Expected result. The result reports the negotiated protocol and cipher and the certificate. --no-system-trust leaves the system trust store out of the check.
SupportAssistTool network tls --host vbr01 --port 443 --compare-versions
To test a UDP port, do the following:
  1. On the other machine, run network udp listen --port PORT --seconds 60.
  2. Run network udp test --host HOST --port PORT --sat-listener.
  3. Read the result. Without a SAT listener to acknowledge, a UDP test is indeterminate.
Expected result. A cooperating SAT listener makes the result verified.
SupportAssistTool network udp test --host vbr01 --port 9401 --sat-listener

Testing toward this machine

A listener puts a temporary endpoint on a port so the other end can be tested toward this machine. It stops when the command stops.

To listen for a test from another machine, do the following:
  1. Run network listen --port PORT --seconds 60. Add --multiple to accept more than one connection.
  2. Run the test from the other machine against this machine's address and the port.
  3. Read the connections the listener prints.
Expected result. The listener prints each connection with its address. --banner TEXT sets the line sent to each client, with %port% filled in, and --banner "" sends none. The default banner says SAT is listening on the port.
SupportAssistTool network listen --port 6160 --seconds 60 --multiple
SupportAssistTool network udp listen --port 9401 --seconds 60

When network test reaches a SAT listener, the two ends exchange a handshake and a test payload whose SHA-256 is checked on arrival. That proves the data path end to end, not only that the port accepts a connection. network udp listen takes --single to stop after one probe.

Throughput

To measure throughput between two machines, do the following:
  1. On the receiving machine, run network throughput server --port 2500.
  2. On the sending machine, run network throughput client --host HOST --port 2500 --bytes 1G.
  3. Read the rate the link sustained for the bytes sent.
Expected result. The server waits 60 seconds for the client by default; --connect-timeout-ms and --idle-timeout-ms change the waits. The test loads the network while it runs.
SupportAssistTool network throughput server --port 2500

System checks

  • system pending-restart says which restart marker is set, when, and the events that name the cause. It exits 3 when the system needs a restart.
  • system host-checks reads what most often explains a failed snapshot or backup. On Windows: backup events (volsnap, VSS, disk and NTFS) over --days, 7 by default, the Veeam drivers, VSS shadow storage, and the .NET and TLS registry values. On Linux: the Veeam snapshot module and the kernel log. --checks takes a list such as events,drivers; without it every check for the system runs. It exits 3 on a finding.
  • system pipes lists the named pipes on Windows and the Unix domain sockets on Linux, with the Veeam, SQL Server and PostgreSQL ones named. --veeam lists the Veeam and database ones only. Nothing is opened or connected to.
  • system installer-cache (Windows) lists the installed products with an UpgradeCode (--upgrade-code) or whose name or publisher holds a text (--name, Veeam when neither is given), with their version, install date, original package, PackageCode, last used source and the cached package Windows keeps in C:\Windows\Installer, present or missing, and their patches. --check reads an .msi, an .exe or a folder (four levels down, such as a mounted ISO) and shows each file's identity and SHA-256, and whether an .msi is the package a product was installed from (the same PackageCode). It exits 3 when a cached package is missing.
  • wmi health (Windows) checks WMI in stages: the Winmgmt service and the services it depends on, the repository's consistency (as administrator) and size, a timed probe of each namespace Veeam reads, and the WMI faults logged in the last 7 days, each row with Pass, Finding, Not present, Needs administrator or This machine only. --machine checks another machine's service and namespaces; its repository and event logs are read only on that machine itself. It exits 3 when a row is a finding.
  • wmi query --machine HV01 --user CONTOSO\admin --preset cluster (Windows) signs in to HV01 as that account and reads its password from the SAT_WMI_PASSWORD environment variable; the connection is then encrypted. Without --user, another machine is signed in to as the account SAT runs as. --user takes DOMAIN\name, name@domain or a name alone for an account of that machine, and is refused for this machine.
To run the system checks, do the following:
  1. Run system pending-restart, then system host-checks --days 30.
  2. On Windows, run system installer-cache --name Veeam --check D:\ and wmi health.
  3. Read the status of each row. Exit 3 marks a finding.
Expected result. The rows name what was read and what was found.
SupportAssistTool system pending-restart

SupportAssistTool system installer-cache --name Veeam --check D:\

SupportAssistTool wmi health

  5. Add --email to print only the email text.
Expected result. The lowest speed sets the time.

Change analysis

Comparing file and registry metadata between two points in time, to see what changed on a machine between a working state and a broken one.

Before You Begin

  • Choose the folder to look at and the capture file to write, such as before.satsnap.
  • Run as administrator or root to read the places that need it. They are listed as skipped without it.
  • Keep the folder where it was captured when you compare with --live.
To find what changed under a folder, do the following:
  1. Run files baseline --path DIR --output before.satsnap.
  2. Make the change, or wait for it.
  3. Run files compare --baseline before.satsnap --live --output changed.html --format html.
  4. Add --keep to keep the compare in the capture file.
Expected result. The report lists what was added, removed, changed and moved or renamed.
SupportAssistTool files baseline --path /opt/veeam --output before.satsnap
# ... the change happens ...
SupportAssistTool files compare --baseline before.satsnap --live \
    --output changed.html --format html

--live compares the baseline against the machine as it is. --other compares two saved baselines, which is how a working machine is compared with a broken one.

OptionWhat it does
--path DIR, --output FILEThe folder to capture and the capture file to write.
--hash none|all|below-size|extensionsWhich files are read for a SHA-256. --hash-max-bytes N sets the size limit and --hash-extension .log names an extension.
--exclude PATTERNLeaves matching paths out.
--maximum-depth N, --maximum-objects NLimit how deep and how many objects are read.
--follow-reparseFollows reparse points.
--batch-size NHow many entries the capture writes to its file at a time; 1000 to begin with. registry baseline takes it too.
--no-file-idWindows: does not record each file's volume serial number and file ID.
--hydrate-cloud-filesWindows: reads a cloud file that is not stored on the machine, such as a OneDrive placeholder, for its SHA-256, which downloads it. Without it such a file is not read.
--baseline FILE, --baseline-id IDThe capture to compare, and which capture in the file.
--live or --other FILECompare with the machine as it is, or with a second capture.
--other-id IDWhich capture in the second file.
--timestamp-tolerance-100ns NTimes that differ by no more than N units of 100 nanoseconds count as the same.
--no-move-detectionLists a moved file as one removed and one added.
--no-hash-inferenceDoes not take two files with the same SHA-256 for one file that moved.
--keepKeeps the compare in the --baseline file: when it ran, what it was compared with, the counts and every row.
--output FILE, --format text|html|json|csvWhere the report is written, and in which form.

On Windows, a baseline captured as administrator on an NTFS volume also records the change journal's position, and the compare reads the journal from there. It adds a created-and-deleted row for each file or folder created and removed in between, which the two captures cannot show, and a renamed row for each rename. --no-journal leaves the journal out. A files baseline taken as administrator of a folder on a local NTFS volume is read from the volume's master file table, and otherwise folder by folder; --live reads the machine the way the baseline was read. The System Differences page keeps every compare in the capture file in the same way.

To read what a capture holds, do the following:
  1. Run baseline inspect --file before.satsnap.
  2. Run baselines list --folder ./baselines to list the captures in a folder.
Expected result. The output shows what the capture covers, how a files baseline was read (Read from:) and the compares kept in it. snapshots list and snapshot inspect are the same verbs under their older names.
SupportAssistTool baselines list --folder ./baselines
SupportAssistTool baseline inspect --file before.satsnap

File baselines work on both platforms; the Windows options for alternate data streams, file IDs and cloud hydration are rejected on Linux. Registry baselines are Windows only and are listed under Windows-only verbs.

On Windows, tools run --id etl2pcapng --input capture.etl --output capture.pcapng converts an ETL capture. iperf client and iperf server run iPerf3 when it is present; --tools-root points at the folder that holds it, and --arg passes an extra argument to iPerf3 and can be given more than once. Each of these tools is optional: a missing tool makes the related verb report itself unavailable and does not affect anything else.

Using SAT from a script

The CLI is meant to be scripted: test capabilities first, then branch on exit codes.

#!/bin/bash
set -u
./SupportAssistTool logs review --path "$1" --output review.txt
case $? in
  0) echo "reviewed, no findings" ;;
  3) echo "reviewed, findings present" ;;
  2) echo "not applicable on this host" ;;
  *) echo "review failed"; exit 1 ;;
esac

Most commands accept --json for machine-readable output. On Windows, output redirection and pipes work normally, so > file and | findstr behave as expected.

To run SAT from a script, do the following:
  1. Run capabilities --json and test it before calling a platform-specific verb.
  2. Run the command, with --json where the output is read by another program.
  3. Branch on the exit code.
  4. Put a password in an environment variable (SQLCMDPASSWORD, PGPASSWORD, SAT_WMI_PASSWORD) before the command. No option takes a password.
Expected result. The script reads the exit code and the JSON, not the text.

What is collected

Collections are bounded to what a support case needs.

  • Veeam product logs, and the platform context needed to read them.
  • Third-party error logs are sanitised before inclusion, and can be excluded with --no-third-party-errors.
  • The vendor's own exporters run only when --official-exporters is given.
  • Remote credentials are held for the session only and are not written to disk. Private keys are not exported.
  • Registry values that look secret-like are redacted in Environment Review output.

Review a collection before sending it.

Troubleshooting

The common problems and their fixes.

SymptomCause and fix
The executable will not start on LinuxThe lib directory is not beside it. Run from the unpacked package; a binary copied out of it does not start.
version works but a verb reports 'not available'The verb is for the other platform, or a capability is missing. Run capabilities to see what this build can do here.
A reading is skipped and mentions approvalIt needs elevation. Run diagnostics to confirm, and elevate only where the machine's owner allows it.
An archive parses to 'No log files could be extracted'The extraction path was too long for the platform. Point --output at a shorter directory.
Exit code 3 is treated as failure by a script3 means the command completed and found something. Test for it explicitly.
files hash exits 64 with --expectThe value is not 64 hexadecimal characters. Copy the whole SHA-256 value; spaces and letter case do not matter.
Running SAT with a path opens the window and runs no commandEvery argument was an existing path, which is how the desktop starts SAT for dropped files. Put a command first, for example files hash --path.
